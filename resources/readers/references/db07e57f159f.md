# 数据与工程主题域

## 主题主线

> 数据工程的目标不是“把数据送到下游”，而是让每个下游都能回答：这条数据当时是否可得、语义是否完整、状态是否可重建、处理是否可恢复、结果是否可审计。

本主题域把四种岗位放进同一条能力闭环：

**原始事件与版本 → 点时可得性 → 状态重建 → 因果时间对齐 → 流批计算与分层存储 → 性能和故障证据 → 研究、回测、执行、风控消费**

资料中的工具名只是实现候选。真正需要掌握的是不变量、失败语义、验证指标和岗位交付物。

## 总体系统模型

| 层 | 输入 | 核心状态 | 输出 | 不能破坏的不变量 |
|---|---|---|---|---|
| 接入层 | 交易所/供应商报文、公告、参考数据 | 通道序列、协议和来源版本 | 原始不可变事件 | 原报文可追溯；不能因解析失败丢失证据 |
| 规范层 | 原始事件 | canonical schema、单位、代码、交易日历 | 标准事件 | 原始语义和精度不被悄悄改写 |
| 点时层 | 标准事件、修订、公司行动 | 可得时间、有效时间、版本和质量状态 | `as-of` 可查询快照 | 决策时不可见的数据不能出现在输入中 |
| 状态层 | 快照、增量、成交和撤单 | 订单簿、窗口、持仓、检查点 | 状态/特征流 | 单键顺序、幂等、恢复后不漏不重 |
| 服务层 | 状态和历史数据 | 缓存、索引、模型/规则版本 | 研究、回测、执行、风控接口 | 同一版本和输入可重现 |
| 证据层 | 日志、指标、trace、数据血缘 | SLO、告警和审计记录 | 故障定位与验收证据 | 可观测性不能静默改变热路径语义 |

## 四种岗位的阅读路径

- **量化数据工程师：**先读 01、02、03，再读 04 和 05；重点是契约、质量、状态恢复与数据产品 SLO。
- **量化回测平台架构师：**先读 01、03、04，再读 02 和 05；重点是可得时点、确定性回放、分布式状态与黄金结果。
- **量化开发工程师：**先读 02、05，再读 03、04 和 01；重点是协议、内存/网络路径、可观测性和兼容发布。
- **交易策略研究员：**先读 01、03、02，再读 05 和 04；重点是因果输入、微观结构偏差、成本后有效性和实盘归因。

## 使用约定

1. 先在主题页中闭卷回答“主动回忆”，再沿“来源导航”进入原章节和叶题。
2. 页面中的组件组合属于**设计建议**，不是唯一标准架构；阈值、性能数字和云/交易所能力必须在目标环境重新验证。
3. `point-in-time`、`Exactly-Once`、`低延迟`、`跨市场同步`都必须写出适用边界，不能只用名词作结论。
4. 法规、交易所规则、数据许可和云产品能力仅按题库知识整理，不代表截至当前日期已核验。

## 综合自检

- [ ] 能从一条原始报文画到策略决策，并标出全部时间戳、版本、状态和失败点。
- [ ] 能解释为什么“数值正确”不等于“点时正确”。
- [ ] 能在订单簿缺口、跨市场时钟漂移、流式背压和尾延迟飙升之间建立因果排查顺序。
- [ ] 能为每项性能优化给出正确性对账、压力测试、故障回退和审计证据。
- [ ] 能说明四种岗位在同一事故中的不同责任和交付物。
