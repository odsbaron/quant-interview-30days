## 知识框架

### 5.1 Tick数据清洗与异常值处理

- **核心概念：**低延迟管道中的清洗聚焦多源 Tick 的乱序、缺失、重复和异常，同时要求输出一致。
- **方法 / 系统组件：**接入层校验序列与 schema，流引擎按事件时间重排并运行稳健阈值/业务规则，状态与修复记录用检查点、幂等输出和回放保障；大面积乱序先隔离再重建。
- **指标 / 约束：**以乱序率、修复率、误报率、清洗耗时和数据完整率衡量；不能在未知缺口上继续生成策略数据。

### 5.2 高效存储与查询订单簿数据

- **核心概念：**订单簿存储面对高写入、状态更新和历史范围查询，适合热温冷分层。
- **方法 / 系统组件：**最新盘口放内存/键值或时序引擎，近线分析放 ClickHouse，历史放 Parquet；使用价格/数量差分、快照+增量、标的时间分区和预聚合索引。
- **指标 / 约束：**压缩要支持局部恢复和精确数值；关注写放大、热点、查询分位延迟、恢复速度和成本。

### 5.3 低延迟数据传输与协议选择

- **核心概念：**传输选型涉及 TCP/UDP、组播、FIX/WebSocket、Protobuf/FlatBuffers 与网络拓扑，可靠性和时延不可脱离业务讨论。
- **方法 / 系统组件：**行情可用 UDP/组播加应用层序列与重传，控制/交易链路偏 TCP/FIX；紧凑定长或零拷贝序列化，网络抖动用小窗口重排，固定解析可下沉 FPGA。
- **指标 / 约束：**分解发送、网络、排队、解码延迟，并监控丢包、乱序、重传和带宽；FlatBuffers 的低解码开销需与兼容性权衡。

### 5.4 实时流处理框架的应用与优化

- **核心概念：**流框架由 source、算子、窗口/事件时间、状态后端、检查点和 sink 组成，Flink 真流与 Spark 微批有不同延迟模型。
- **方法 / 系统组件：**订单簿状态按标的分区，窗口配置事件时间/水位线/允许迟到；采用增量检查点、本地恢复、状态 TTL 和对齐优化，Exactly-Once 贯通可重放 source 与事务/幂等 sink。
- **指标 / 约束：**检查点间隔、状态大小、水位线停滞、背压和跨境链路是主要约束；优化不可破坏一致性语义。

### 5.5 高并发低延迟数据管道的架构设计

- **核心概念：**高并发架构关注消息分发、计算分片、状态恢复和吞吐—延迟曲线，Kafka 与 ZeroMQ 代表持久日志和轻量通信两类取舍。
- **方法 / 系统组件：**按交易所/标的分片，日志层可回放，计算层无共享或局部状态，检查点+WAL+幂等保障恢复；用弹性扩缩、过载保护和分级降级应对洪峰。
- **指标 / 约束：**设定延迟 SLO、峰值吞吐、恢复时间/恢复点和数据准确率；第 5.5.7 源稿仅有“题目解读”，复习时不可把缺失原文当作完整答案。

### 5.6 数据管道的性能瓶颈分析与优化

- **核心概念：**瓶颈可来自网络、序列化、锁/线程、CPU、内存、磁盘、状态和数据倾斜，必须以观测证据定位。
- **方法 / 系统组件：**建立端到端追踪、队列积压与资源剖析，先复现和分段测量，再按原因做异步 I/O、多线程、批量、向量化、分区重平衡或网络就近部署，最后压测回归。
- **指标 / 约束：**用延迟分位数而非平均值，兼看吞吐、错误、GC、缓存命中和成本；优化一次只改变可归因变量。

## 题型与答题框架

- **概念 / 说明题（3 题）：**先给出对象的精确定义与数据边界，再说明字段或组成、工作机制、量化岗位用途，最后补充不适用条件和常见混淆。
- **方案设计 / 故障处理题（21 题）：**按“输入与语义 → 清洗/计算 → 状态与存储 → 输出 → 监控与恢复”展开；排障题先建立基线并分层定位，再给验证实验、修复和回归。
- **比较 / 选型题（5 题）：**先固定负载和 SLO，再从延迟、吞吐、一致性、状态/查询模式、容错、成本、运维与合规逐维比较，给出条件化结论而非绝对优劣。
- **案例 / 复盘题（6 题）：**交代业务规模与约束，给出原始指标和证据，说明定位过程、关键改动、验证口径、剩余风险；没有亲历数据时使用明确的假设案例。

本章的答案最终要落到可验证约束，例如：以乱序率、修复率、误报率、清洗耗时和数据完整率衡量；压缩要支持局部恢复和精确数值；分解发送、网络、排队、解码延迟，并监控丢包、乱序、重传和带宽；检查点间隔、状态大小、水位线停滞、背压和跨境链路是主要约束；设定延迟 SLO、峰值吞吐、恢复时间/恢复点和数据准确率；用延迟分位数而非平均值，兼看吞吐、错误、GC、缓存命中和成本。

## 高频易错点

- 只给组件清单没有延迟预算。
- 用 UDP 后不设计序列/重传。
- 把 Kafka 与 Flink 当同类替代品。
- 检查点调少却不分析恢复代价。
- 性能优化无基线与回归验证。
