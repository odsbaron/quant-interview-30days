## 本章定位

本章是有状态实时计算核心：围绕事件时间、背压、容错、状态与端到端一致性构建金融流管道。

回答本章问题时，不应停留在工具名罗列；需要把数据语义、处理步骤、系统状态、验证指标和失败边界连成闭环。

## 知识框架

### 11.1 数据流与实时处理基础

- **核心概念：**数据流是持续、无界事件序列，实时处理需事件时间、窗口、状态与持续输出。
- **方法 / 系统组件：**比较 Flink 的分布式有状态流和 Kafka Streams 的嵌入式流库；滑窗波动率加入时间衰减与异常处理，Tick 初始特征含收益、价差、量和订单流。
- **指标 / 约束：**区分事件时间与处理时间，监控新鲜度、吞吐、积压和水位线；窗口输出不能包含未来事件。

### 11.2 低延迟处理技术

- **核心概念：**低延迟流处理同时处理高频、不规则、乱序和完整性问题。
- **方法 / 系统组件：**紧凑协议、异步/并行、内存状态和硬件加速缩短路径，水位线与小型重排缓冲处理乱序，序列号/校验和/跨源验证保障完整。
- **指标 / 约束：**定义允许迟到和丢失策略；优化需看端到端尾延迟与错误率，不能只看算子耗时。

### 11.3 容错与故障恢复

- **核心概念：**容错目标是检测故障、隔离影响、恢复状态、重放数据并避免重复副作用。
- **方法 / 系统组件：**心跳/指标发现故障，副本与故障转移维持服务，Checkpoint 或日志恢复状态，offset/序列号断点续传，幂等/事务输出实现连续处理。
- **指标 / 约束：**比较恢复时间、恢复点、检查点开销和日志重放长度；市场异常与系统故障须用不同处置路径。

### 11.4 性能优化与高吞吐量处理

- **核心概念：**吞吐问题通过背压暴露，瓶颈可能在消费、状态、内存、消息系统、倾斜或硬件。
- **方法 / 系统组件：**沿 source 到 sink 看背压与队列，调并行度/分区和资源，控制输入速率，优化对象/内存池，Kafka/Pulsar 按日志架构与运维需求选型，GPU/FPGA 加速热点。
- **指标 / 约束：**背压是保护机制而非根因；扩容前要排除数据倾斜，观察吞吐、尾延迟、积压、GC 和状态大小。

### 11.5 状态管理与一致性

- **核心概念：**状态管理保存窗口、聚合和盘口等跨事件信息，一致性取决于事件时间、快照与外部输出协同。
- **方法 / 系统组件：**keyed state 按标的分区，Checkpoint 对齐 source offset 与状态，sink 用两阶段提交或幂等；Savepoint 用于运维迁移，Checkpoint 用于自动容错。
- **指标 / 约束：**处理迟到、TTL、状态膨胀和 schema 演进；Exactly-Once 是端到端属性，不能只凭框架内部检查点宣称。

### 11.6 流处理框架概述

- **核心概念：**框架选型涉及真流/微批、状态、事件时间、背压、生态与运维。
- **方法 / 系统组件：**Spark Streaming 通过批间隔、接收速率和动态反压治理微批，Flink 用检查点保证状态一致，Kafka Streams 用本地状态库和 changelog 做窗口计算。
- **指标 / 约束：**以目标延迟、状态规模、恢复、吞吐和团队能力实测；框架名称不等于自动满足金融准确性。

### 11.7 实时数据管道设计

- **核心概念：**实时管道包含 source、传输、处理、状态、存储/sink、监控与容错。
- **方法 / 系统组件：**Kafka 侧重持久传输与回放，Flink 侧重有状态计算；背压通过限速、扩容、降级与优化下游处理，检查点/重放/幂等维护准确性。
- **指标 / 约束：**设计须给出延迟预算、峰值容量、顺序键、恢复语义、告警和降级边界。

## 题型与答题框架

- **概念 / 说明题（8 题）：**先给出对象的精确定义与数据边界，再说明字段或组成、工作机制、量化岗位用途，最后补充不适用条件和常见混淆。
- **方案设计 / 故障处理题（22 题）：**按“输入与语义 → 清洗/计算 → 状态与存储 → 输出 → 监控与恢复”展开；排障题先建立基线并分层定位，再给验证实验、修复和回归。
- **比较 / 选型题（5 题）：**先固定负载和 SLO，再从延迟、吞吐、一致性、状态/查询模式、容错、成本、运维与合规逐维比较，给出条件化结论而非绝对优劣。
- **案例 / 复盘题（7 题）：**交代业务规模与约束，给出原始指标和证据，说明定位过程、关键改动、验证口径、剩余风险；没有亲历数据时使用明确的假设案例。

本章的答案最终要落到可验证约束，例如：区分事件时间与处理时间，监控新鲜度、吞吐、积压和水位线；定义允许迟到和丢失策略；比较恢复时间、恢复点、检查点开销和日志重放长度；背压是保护机制而非根因；处理迟到、TTL、状态膨胀和 schema 演进；以目标延迟、状态规模、恢复、吞吐和团队能力实测；设计须给出延迟预算、峰值容量、顺序键、恢复语义、告警和降级边界。

## 高频易错点

- 混淆 Kafka 与 Flink 职责。
- 背压当故障根因而非信号。
- 处理时间代替事件时间。
- Checkpoint 与 Savepoint 混用。
- 只保证框架内状态而忽略外部输出。

## 复习顺序

1. **核心必会：**先掌握 11.1—11.3 的流/窗口/低延迟与故障恢复。
2. **进阶：**再攻克 11.4—11.7 的背压、状态后端、框架选型和完整管道。
3. **查漏：**重点复查水位线、迟到、Checkpoint/Savepoint、sink 副作用和积压。
