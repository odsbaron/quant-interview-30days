# 执行、风控与治理

## 主题域定位

本域承接 Wiki 总主线的后半程：

> 研究信号只有经过可解释的订单状态机、可降级的实时风控和可重放的治理证据，才从“理论可交易”变成“执行可达、风险可控、责任可审计”。

这里关注的是**交易语义与证据链**：一笔意图怎样变成母单、子单、交易所回报、成交、持仓和成本；异常怎样被检测、确认、处置和恢复；代码、规则、数据、模型与审批怎样共同证明当时为什么这样交易。

本域不重复数据工程主题中的 CPU 缓存、内核旁路、网卡调优或通用流处理实现。相关技术只有在影响订单语义、风控动作、恢复一致性或审计证据时才会出现。

> **时效边界：**本域涉及的法规名称、交易所规则、监管字段、保存期限、阈值和前沿技术能力，均为现有题库的学习整理，**不是截至当前日期的时效核验**。用于实务前必须由合规、法务或系统责任人依据适用市场和最新官方文件复核。

## 一条贯穿五页的证据链

```text
策略意图/模型版本
  → 母单目标与硬约束
  → 子单与报单前风控
  → 网关/交易场所受理
  → 撤单、拒单、部分成交、最终成交
  → 持仓/资金/风险状态
  → 成本与市场影响归因
  → 规则、数据、代码、审批、回放证据
```

每一个箭头都应回答四个问题：

1. **输入是否在当时可得？** 防止用未来行情、事后修订数据或当前规则解释历史决定。
2. **状态由什么事件推进？** 防止重复回报、乱序和网络重连造成二次副作用。
3. **失败后进入什么安全状态？** 防止自动恢复过早或人工处置绕开风控。
4. **如何复现并证明？** 防止只有最终报表而没有原始事件、版本和审批链。

## 推荐学习顺序

1. 先读订单生命周期、撮合与执行（原本地参考：`01_订单生命周期、撮合与执行.md`），掌握交易对象和状态语义。
2. 再读实时风控、熔断与故障恢复（原本地参考：`02_实时风控、熔断与故障恢复.md`），把状态异常映射为可控动作。
3. 然后读合规、审计与数据治理（原本地参考：`03_合规、审计与数据治理.md`），补齐证据、权限与监管沟通。
4. 用测试、交付与安全工程（原本地参考：`04_测试、交付与安全工程.md`）验证上述语义不会被变更或故障破坏。
5. 最后读前沿技术的评估边界（原本地参考：`05_前沿技术的评估边界.md`），学习如何在强经典基线和安全回退下做探索。

## 闭卷总案例

某策略在行情源切换后连续出现部分成交、重复成交回报和撤单拒绝；风险系统发现净头寸超限后进入暂停状态。随后团队发现当日刚发布了新的风控字段映射和模型版本。

闭卷回答时，请画出：

- 从策略意图到成交和净头寸的完整事件序列；
- 哪些事件必须有幂等键，哪些状态必须原子迁移；
- 系统应进入何种降级状态，恢复需要满足哪些独立条件；
- 如何区分数据异常、系统故障、策略问题和真实市场冲击；
- 需要冻结哪些代码、配置、模型、行情、订单、审批和发布证据；
- 如何用确定性回放证明修复既没有重复成交，也没有掩盖合规问题。

能够完整回答这个案例，说明五个主题页已经形成一条闭环，而不是五组术语。
